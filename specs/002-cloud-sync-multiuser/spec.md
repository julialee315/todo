# Feature Specification: 다중 사용자 클라우드 동기화 Todo

**Feature Branch**: `002-cloud-sync-multiuser`
**Created**: 2026-05-22
**Status**: Draft
**Input**: User description: "현재 localStorage에 저장되는 단일 사용자 Todo 앱을, Supabase를 활용한 다중 사용자 클라우드 동기화 앱으로 전환한다. 기존 4개 화면(로그인/메인/캘린더/통계)의 시각 구성과 모든 기존 상호작용은 그대로 유지하고, 데이터의 출처만 localStorage에서 사용자별 클라우드로 옮긴다. 인증(이메일/비밀번호 + Google), 사용자별 클라우드 데이터, 멀티 디바이스 실시간 동기화를 단계적으로 도입한다."

## User Scenarios & Testing *(mandatory)*

### User Story 1 — 이메일/비밀번호 인증 (Priority: P1)

새 방문자가 앱을 열어 자기 계정을 만들고, 다음번에 같은 자격으로 다시 들어와 자기 작업 공간을 만난다. 사이드 네비게이션의 로그아웃 버튼으로 세션을 종료할 수 있고, 새로고침해도 로그인 상태가 유지된다. 로그인하지 않은 사람은 메인·캘린더·통계 페이지에 직접 접근할 수 없다.

**Why this priority**: 인증이 없으면 그 위에 얹히는 모든 사용자별 데이터·동기화·소셜 로그인이 성립할 수 없다. 다른 어떤 user story도 P1 없이는 시작될 수 없는, 유일한 의존-루트(stories root) 스토리다.

**Independent Test**: 시드 데이터만 있는 로컬 상태에서도, 가입 → 로그인 → 새로고침 → 로그아웃 → 보호 라우트 리다이렉트의 한 사이클을 별도 데이터 없이 검증할 수 있다. 클라우드 데이터(US2) 없이도 단독으로 동작·검증 가능하다.

**Acceptance Scenarios**:

1. **Given** 가입하지 않은 방문자가 로그인 화면을 보고 있을 때, **When** 유효한 이메일과 8자 이상 비밀번호를 입력해 회원가입을 제출하면, **Then** 계정이 생성되고 메인 화면으로 이동한다.
2. **Given** 이미 가입된 사용자가 로그인 화면에 있을 때, **When** 자신의 이메일·비밀번호로 로그인을 제출하면, **Then** 메인 화면으로 이동한다.
3. **Given** 메인 화면에 있는 로그인 사용자가 있을 때, **When** 페이지를 새로고침하면, **Then** 로그인 상태가 그대로 유지된다.
4. **Given** 로그인 사용자가 있을 때, **When** 사이드 네비게이션의 로그아웃 버튼을 누르면, **Then** 세션이 종료되고 로그인 화면으로 돌아간다.
5. **Given** 로그인하지 않은 방문자가 있을 때, **When** 주소창에 `/main`, `/calendar`, 또는 `/stats`를 직접 입력하면, **Then** 로그인 화면으로 리다이렉트된다.
6. **Given** 사용자가 로그인을 시도할 때, **When** 잘못된 비밀번호를 입력하면, **Then** 화면에 "이메일 또는 비밀번호가 올바르지 않습니다" 같은 사람이 읽을 수 있는 오류가 표시된다.
7. **Given** 사용자가 회원가입을 시도할 때, **When** 이미 가입된 이메일을 입력하면, **Then** "이미 가입된 이메일입니다" 안내와 함께 로그인 쪽으로 유도된다.

### User Story 2 — 사용자별 클라우드 데이터 (Priority: P2)

로그인한 사용자는 자기 할 일만 본다. 다른 사용자의 데이터는 어떤 경로로도 노출되거나 수정되지 않는다. 추가·수정·완료·별표·삭제·서브태스크·우선순위·카테고리·정렬·뷰 같은 모든 변경은 즉시 클라우드에 반영되고, 다른 기기에서 같은 계정으로 로그인하면 같은 상태가 보인다. 처음 로그인한 사용자에게는 기존 샘플 시드(14개 가량)가 자동으로 채워져 빈 화면이 아니라 친근한 출발점에서 시작한다.

**Why this priority**: P1의 인증을 실제로 가치 있게 만드는 핵심 스토리. P3(실시간)와 P4(소셜)는 P2 없이도 의미가 없거나 떨어진다.

**Independent Test**: P3 없이도, 한 사용자가 가입·로그인 → 시드 표시 확인 → 할 일을 추가·완료·별표·삭제 → 로그아웃 → 다시 로그인했을 때 같은 상태가 보이는지로 단독 검증 가능. 또한 두 명의 다른 사용자가 각자 데이터를 만들고, 서로의 데이터가 보이지 않는지를 격리 테스트로 확인 가능.

**Acceptance Scenarios**:

1. **Given** 한 번도 로그인한 적 없는 새 사용자가 로그인을 마쳤을 때, **When** 메인 화면이 처음 로드되면, **Then** 기존 프로토타입과 동일한 샘플 시드(약 14개 할 일, 5개 카테고리)가 그 사용자의 데이터로 채워져 표시된다.
2. **Given** 두 명의 서로 다른 사용자 A·B가 있을 때, **When** A가 자기 할 일을 추가·수정·삭제하더라도, **Then** B의 데이터에는 어떠한 변화도 보이지 않는다.
3. **Given** 로그인 사용자가 메인 화면에 있을 때, **When** 할 일을 추가·완료·별표·서브태스크 추가·우선순위 변경·카테고리 변경 중 하나를 수행하면, **Then** 그 변경은 2초 이내에 클라우드에 저장되고, 로그아웃 후 다시 로그인해도 같은 상태로 남아 있다.
4. **Given** 로그인 사용자가 뷰(오늘/예정/지남 등)나 정렬을 바꿨을 때, **When** 다음 세션에 다시 로그인하면, **Then** 마지막으로 선택한 뷰·정렬이 그대로 복원된다.
5. **Given** 한 사용자의 같은 계정이 다른 기기·브라우저에서 로그인했을 때, **When** 메인 화면이 로드되면, **Then** 이전 기기에서 마지막으로 본 상태와 동일한 할 일·서브태스크·선호도가 표시된다.
6. **Given** 악의적 사용자가 다른 사용자의 자원 식별자를 직접 호출해 데이터를 가져오려 할 때, **When** 그 요청이 시스템에 도달하면, **Then** 시스템은 해당 데이터를 반환하지 않고 접근을 거부한다.

### User Story 3 — 멀티 디바이스 실시간 동기화 (Priority: P3)

한 사용자가 두 개 이상의 탭/기기에서 동시에 앱을 열고 있다. 한쪽에서 할 일을 추가·수정·삭제하면, 다른 쪽 화면에 새로고침 없이 2초 이내에 반영된다. 동시 충돌은 가장 최근 변경이 이긴다.

**Why this priority**: P2 없이는 무의미한 부가 스토리. 단일 기기로도 P2까지로 충분히 가치 있는 앱이 성립하므로 P3는 향상이다.

**Independent Test**: 같은 계정으로 두 탭을 열어 한쪽에서 변경, 다른 쪽에서 자동 반영을 관찰하는 것만으로 단독 검증 가능. P4(소셜 로그인)와는 무관하게 검증된다.

**Acceptance Scenarios**:

1. **Given** 같은 사용자로 탭 A와 탭 B가 메인 화면에 열려 있을 때, **When** 탭 A에서 새 할 일을 추가하면, **Then** 2초 이내에 탭 B의 목록에도 동일한 항목이 나타난다(수동 새로고침 없이).
2. **Given** 두 탭이 같은 사용자로 열려 있을 때, **When** 탭 A에서 한 할 일의 제목을 수정하면, **Then** 2초 이내에 탭 B에서 같은 항목의 제목이 갱신된다.
3. **Given** 두 탭이 같은 할 일을 보고 있을 때, **When** 두 탭이 같은 시각(1초 이내)에 그 항목의 제목을 서로 다른 값으로 동시에 수정하면, **Then** 더 늦은 변경 값으로 양쪽 탭이 수렴한다.
4. **Given** 두 탭이 같은 사용자로 열려 있을 때, **When** 탭 A에서 할 일을 삭제하면, **Then** 2초 이내에 탭 B의 목록에서도 그 항목이 사라진다.

---

### User Story 4 — Google 소셜 로그인 (Priority: P4)

새 계정을 또 만들고 싶지 않은 사용자가 "Google로 계속하기" 버튼 하나로 가입·로그인을 끝낸다. 같은 Google 계정으로 다시 돌아오면 이전 상태가 그대로다. 이메일/비밀번호 로그인은 그대로 공존한다.

**Why this priority**: 가입 마찰을 줄이는 향상. 핵심 가치(개인 클라우드 Todo)는 P1~P3로 이미 완성된다. P4는 편의/리텐션 측면의 + α.

**Independent Test**: Google OAuth 플로우만으로 가입 → 메인 도착 → 로그아웃 → 같은 Google 계정으로 재로그인 시 동일 데이터 확인. 이메일/비밀번호와 무관하게 단독 검증 가능.

**Acceptance Scenarios**:

1. **Given** 한 번도 가입한 적 없는 방문자가 로그인 화면을 보고 있을 때, **When** "Google로 계속하기"를 누르고 Google에서 권한을 승인하면, **Then** 자동으로 계정이 만들어지고 시드 데이터와 함께 메인 화면에 도착한다.
2. **Given** 이전에 Google로 가입했던 사용자가 다시 로그아웃 상태로 돌아왔을 때, **When** "Google로 계속하기"를 다시 누르면, **Then** 이전에 만든 할 일들이 그대로 보인다.
3. **Given** 로그인 화면이 표시될 때, **When** 사용자가 보고 있으면, **Then** 이메일/비밀번호 입력 영역과 "Google로 계속하기" 버튼이 함께 보이며 둘 다 동작한다.
4. **Given** 사용자가 Google 권한 승인 단계에서 권한을 거부하거나 취소했을 때, **When** 다시 로그인 화면으로 돌아오면, **Then** 적절한 안내 메시지가 표시되고 다른 로그인 방법은 그대로 사용 가능하다.

---

### Edge Cases

- 사용자가 이미 가입된 이메일로 회원가입을 다시 시도하면 어떻게 되나? → 명확한 오류와 함께 로그인 흐름으로 안내.
- 비밀번호를 잊은 사용자는? → v1 범위 밖. Google 로그인으로 우회 가능하다는 점만 안내 (자세한 비밀번호 재설정은 후속 스펙).
- 한 사용자의 토큰이 앱이 열려 있는 동안 만료되면? → 시스템이 백그라운드에서 갱신 시도, 실패 시 로그인 화면으로 보내며 작성 중이던 입력은 보존하지 않는다.
- 같은 이메일을 이메일/비밀번호로 가입한 뒤 같은 이메일의 Google 계정으로 로그인하면? → 별개의 계정으로 취급(자동 연결 없음). v1 범위 밖이며 Assumptions에 명시.
- 일시적인 네트워크 단절 시 사용자가 작성 중이던 변경은? → 오프라인 동안 추가 편집은 막히고 마지막 동기화된 상태가 표시된다. 재연결 시 클라우드 상태로 자동 갱신.
- 시드 데이터를 다 지운 사용자가 다시 로그인하면? → 시드는 첫 로그인에만 1회 채워지고, 이후 비어 있는 상태는 사용자의 명시적 선택으로 존중한다 (다시 채우지 않음).
- 두 탭에서 같은 항목을 같은 순간(밀리초 단위)에 동시 수정하면? → 가장 늦게 도착한 변경이 최종 상태가 된다(last-write-wins).
- 사용자가 자기 데이터가 아닌 다른 자원을 강제로 호출하려 하면? → 시스템이 거부하고 어떤 데이터도 반환하지 않는다.

## Requirements *(mandatory)*

### Functional Requirements

#### 인증 (US1, US4)

- **FR-001**: 시스템은 사용자가 이메일과 비밀번호로 회원가입할 수 있어야 한다.
- **FR-002**: 시스템은 비밀번호가 최소 8자 이상이어야 하며 그렇지 않으면 가입을 거부해야 한다.
- **FR-003**: 시스템은 이미 가입된 이메일로의 중복 가입을 거부하고 사용자에게 분명한 메시지를 제공해야 한다.
- **FR-004**: 시스템은 가입된 사용자가 이메일·비밀번호로 로그인할 수 있어야 한다.
- **FR-005**: 시스템은 사용자가 Google 계정으로 가입·로그인할 수 있어야 한다.
- **FR-006**: 시스템은 로그인된 세션을 페이지 새로고침과 브라우저 재시작(같은 브라우저)을 가로질러 유지해야 한다.
- **FR-007**: 시스템은 사이드 네비게이션에 노출된 로그아웃 컨트롤을 제공해야 하며, 누르면 즉시 세션을 종료해야 한다.
- **FR-008**: 시스템은 로그인하지 않은 방문자가 `/main`, `/calendar`, `/stats` 라우트에 접근하려 할 때 로그인 화면으로 리다이렉트해야 한다.
- **FR-009**: 시스템은 잘못된 로그인 자격, 네트워크 오류, Google 권한 거부 등 인증 실패에 대해 사용자가 이해할 수 있는 한국어 오류 메시지를 표시해야 한다.

#### 사용자별 데이터 격리 (US2)

- **FR-010**: 시스템은 모든 할 일과 서브태스크를 정확히 한 명의 사용자에 귀속시키고, 그 외 사용자에게 절대 노출하지 않아야 한다.
- **FR-011**: 시스템은 어떤 사용자도 다른 사용자의 할 일·서브태스크·선호도를 읽거나 수정·삭제할 수 없게 거부해야 한다(직접 식별자 추측·자원 강제 호출 포함).
- **FR-012**: 시스템은 처음으로 로그인하는 사용자의 작업 공간을 기존 프로토타입의 샘플 시드(약 14개 할 일과 5개 카테고리)로 1회 자동 채워야 한다.
- **FR-013**: 시스템은 시드를 채운 뒤 사용자가 데이터를 비웠더라도 이후 로그인 시 시드를 다시 채우지 않아야 한다.

#### 데이터 영속성 (US2)

- **FR-014**: 시스템은 할 일과 서브태스크의 생성·수정·삭제·완료·별표·우선순위·카테고리 변경을 사용자 동작 시점으로부터 2초 이내에 클라우드에 반영해야 한다.
- **FR-015**: 시스템은 각 사용자의 현재 뷰 선택과 정렬 선호를 클라우드에 저장해 다음 세션 또는 다른 기기에서 동일하게 복원해야 한다.
- **FR-016**: 시스템은 사용자가 같은 계정으로 다른 기기·브라우저에 로그인했을 때 마지막으로 동기화된 상태를 동일하게 보여줘야 한다.

#### 실시간 동기화 (US3)

- **FR-017**: 시스템은 한 사용자의 한 세션에서 발생한 데이터 변경을, 같은 사용자의 다른 열린 세션들에 2초 이내에 수동 새로고침 없이 전달해야 한다.
- **FR-018**: 시스템은 같은 항목에 대한 동시 변경 시 마지막으로 도착한 변경을 최종 상태로 채택해야 한다(last-write-wins).
- **FR-019**: 시스템은 다른 사용자의 세션으로 한 사용자의 변경 이벤트를 절대 전달하지 않아야 한다.

#### 오프라인·복원력

- **FR-020**: 시스템은 네트워크 단절 동안 마지막으로 동기화된 상태를 읽기 전용으로 화면에 유지해야 한다.
- **FR-021**: 시스템은 네트워크가 복구되면 사용자의 개입 없이 클라우드 상태로 자동 갱신해야 한다.
- **FR-022**: 시스템은 오프라인 상태에서 데이터 수정 동작을 허용하지 않거나, 명확한 "오프라인" 안내와 함께 그 동작을 차단해야 한다.

#### 일반·UX

- **FR-023**: 시스템은 기존 4개 화면(로그인/메인/캘린더/통계)의 시각 구성과 모든 기존 상호작용을 동일하게 유지해야 한다 — 데이터 출처만 클라우드로 바뀐다.
- **FR-024**: 시스템은 "오늘" 표시와 상대 날짜 그룹핑을 실제 현재 시각(사용자의 로컬 타임존)으로 계산해야 한다 — 프로토타입의 2026-05-15 고정 클럭을 대체한다.
- **FR-025**: 시스템은 어떤 사용자에게도 다른 사용자의 이메일, 비밀번호, 또는 할 일을 노출하지 않아야 한다.

### Key Entities *(include if feature involves data)*

- **User Account**: 인증된 사람을 나타내는 단위. 속성: 고유 식별자, 이메일, 가입 방법(이메일/비밀번호 또는 Google), 가입 시점. 다른 모든 엔티티의 소유자.
- **Task**: 정확히 한 User Account에 귀속되는 할 일 한 건. 속성: 제목, 완료 여부, 별표 여부, 우선순위(4단계 중 하나), 카테고리(5종 중 하나), 생성/수정 시각. User Account 없이는 존재할 수 없다.
- **Subtask**: 정확히 한 Task에 귀속되는 하위 항목. 속성: 제목, 완료 여부. 부모 Task 없이는 존재할 수 없다.
- **User Preference**: 사용자의 UI 선택을 세션 간 유지하기 위한 단위. 속성: 현재 뷰 선택, 정렬 선택, 테마. 한 User Account 당 하나.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 새 사용자가 회원가입을 시작해 시드가 채워진 메인 화면에 도달하기까지 60초 이내에 완료할 수 있다.
- **SC-002**: 한 사용자의 데이터가 다른 사용자에게 어떤 경로로도 노출되거나 수정되지 않는다 — 자동화된 격리 테스트와 보안 검토에서 100% 통과.
- **SC-003**: 사용자가 변경한 모든 작업(추가·수정·완료·삭제·별표·우선순위·카테고리)이 페이지 새로고침 또는 재로그인 후 99% 이상 그대로 보존된다.
- **SC-004**: 한 사용자의 두 세션 중 한쪽에서의 변경이 다른 쪽에 수동 새로고침 없이 95% 이상 2초 이내에 반영된다.
- **SC-005**: 로그아웃 후 다시 로그인하기까지 15초 이내에 완료할 수 있고, 데이터 상태는 직전 세션과 동일하다.
- **SC-006**: Google 첫 로그인(버튼 클릭→메인 화면 도착) 90% 이상이 30초 이내에 완료된다.
- **SC-007**: 5분 미만의 일시적 오프라인 구간 동안 발생한 데이터 손실·손상이 0건이며, 재연결 후 클라우드 상태로 정확히 복원된다.
- **SC-008**: 기존 4개 화면의 시각·상호작용 회귀가 0건 — 즉 클라우드 전환 이후에도 기존 컴포넌트 테스트와 통합 테스트가 그대로 통과한다.

## Assumptions

- 기존 4개 화면(로그인/메인/캘린더/통계)의 시각 디자인과 모든 기존 상호작용은 그대로 보존된다. 이번 스펙은 데이터 출처를 옮기고 인증·동기화·소셜 로그인을 도입하는 데에 한정된다.
- 클라우드 백엔드는 Constitution v1.1.0에서 허용된 Supabase를 사용한다. 행 수준 격리, OAuth, 실시간 변경 전파를 지원한다는 것이 전제다. (이 스펙의 요구사항 자체는 구현-중립적이다.)
- 이메일/비밀번호와 Google은 별개의 로그인 경로다. 같은 이메일을 양쪽에서 사용해 가입한 경우에도 자동 계정 연결(account linking)은 하지 않는다 — v1 범위 밖.
- 이메일 인증 메일을 통한 가입 확인은 v1 범위 밖이다(가입 즉시 활성화 가정).
- 비밀번호 재설정("비밀번호를 잊으셨나요?") 흐름은 v1 범위 밖이다. 비밀번호를 잃은 사용자는 Google 로그인을 쓰거나 새 계정을 만든다.
- 오프라인 상태에서의 쓰기 큐(offline-first 편집)는 도입하지 않는다. 오프라인 동안 화면은 마지막으로 동기화된 상태를 읽기 전용으로 보여주고, 편집 동작은 차단하거나 안내한다. 온라인 복귀 시 자동 동기화한다.
- "오늘"은 사용자의 로컬 타임존 기준 실제 현재 시각이다. 프로토타입의 2026-05-15 고정 클럭은 이번 마이그레이션 시점에 제거된다.
- 사용자가 시드 데이터를 모두 지운 뒤 다시 로그인하더라도 시드는 재주입되지 않는다 — 사용자의 의도로 본다.
- 시드 데이터 자체는 기존 프로토타입의 약 14개 샘플 할 일과 5개 카테고리 정의를 그대로 사용한다.
- 모바일 반응형, 다국어, 접근성 강화(스크린리더 외 확장 등), 통계 화면의 새 KPI 등은 이 스펙의 범위 밖이다.
- 사용자는 일반적으로 안정된 인터넷 연결을 가진다고 가정한다. 오프라인 지원은 best-effort(읽기 전용 캐시 + 재연결 동기화)다.
